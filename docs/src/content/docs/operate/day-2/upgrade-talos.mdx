## Goal

Move every node of one cluster to a new Talos release, one node at a time.

## Before you start

- You have the kubeconfig of the management cluster.
- A person with `pk-metal-approver` can approve. That is you, if your site allows self-approval. If not, it is a second person. See [](howto:approval-permissions).
- The cluster is `Available`. Each node is `Ready`.
- Talos accepts the new release from the release that each node runs. Talos v1.14 accepts an upgrade from v1.12 or later. The Talos project recommends one minor at a time.
- [](cli:upgrade) refuses a downgrade.
- This pk-metal knows the new release. See [Upgrade pk-metal first](#upgrade-pk-metal-first).
- Optional: a [](kind:MaintenanceWindow) covers the machines. A node outside its window waits.

## Upgrade pk-metal first

pk-metal checks each Talos step against the Talos libraries in its build. A build knows the Talos releases up to its own Talos minor. For a newer minor, [](cli:upgrade) and the rollout plan stop with the message `upgrades to version … are not supported`.

<Steps>

1. Read the Talos version of the libraries in the pk-metal release notes.

2. If the new Talos minor is newer, upgrade pk-metal first.

</Steps>

## Steps

<Callout type="note">
If your TalosCluster is in git, change `spec.talosVersion` there, and use [](cli:upgrade) only to read the plan. Otherwise your GitOps tool writes the old release back. See [](concept:gitops).
</Callout>

<Steps>

1. Ask for the new release. The command changes only the [](kind:TalosCluster) spec. It waits for the proposal and shows the plan.

   ```sh
   pk-metal upgrade talos prod v1.14.7
   ```

   The output names the rollout, for example `prod-talosupgrade-1a2b3c4d`.

2. Approve the plan. If your site forbids self-approval, ask a second person to approve it.

   ```sh
   pk-metal rollout approve prod-talosupgrade-1a2b3c4d
   ```

   The rollout starts on the first control plane.

3. Monitor the first node.

   ```sh
   pk-metal rollout show prod-talosupgrade-1a2b3c4d
   ```

   The `Paused` condition has the reason `PausedAfterFirstNode`.

4. Make sure that the first node runs the new release and is `Ready`.

   ```sh
   kubectl get talosnodes
   ```

   The `VERSION` column shows `v1.14.7` for the first node.

5. Resume the rollout.

   ```sh
   pk-metal rollout resume prod-talosupgrade-1a2b3c4d
   ```

   The other nodes follow, one at a time.

</Steps>

<Callout type="caution">
Do not change `spec.talosVersion` again while a rollout waits for approval.
The plan changes, and the rollout ends with the reason `PlanChanged`.
</Callout>

## Verify

- `pk-metal rollout show <rollout>` shows `Complete=True`.
- `pk-metal status` shows one version in the `TALOS WANT/RUN` column of the cluster.
- Each [](kind:TalosNode) has `VersionCurrent=True`.

## Stop or roll back

- To stop before the next node: `pk-metal rollout pause <rollout>`.
- To stop for good: `pk-metal rollout abort <rollout>`. A node that runs finishes. The other nodes are `Skipped`.
- The operator does not downgrade Talos. [](cli:upgrade) refuses a lower version.

## Staged upgrades

The rollout does not stage an upgrade. A [](act:TalosUpgrade) action with `stage: true` writes the image and reboots the node at once. The upgrade runs early in the next boot. Talos does not drain the node in this mode, so put a `drain` action before it. Use it only when open files stop a normal upgrade.

## If it fails

| What you see | Go to |
| --- | --- |
| The rollout stops with `RolloutFailed` | [](rb:operation-failed) |
| `Progressing` shows `WaitingForHealth` for a long time | [](rb:rollout-paused) |
| `Complete=False` with `PlanChanged` | [](rb:rollout-paused) |
| A drain does not end | [](rb:drain-stuck) |
| A node does not come back | [](rb:node-not-ready) |
