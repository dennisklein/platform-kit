## Symptoms

<dl>
  <dt>Operation</dt>
  <dd>`Failed` at [](act:Drain). The message names the pods that did not leave.</dd>
  <dt>Kubernetes node</dt>
  <dd>`SchedulingDisabled`.</dd>
</dl>

## Impact

The node is cordoned. Its running pods stay. No new pod goes to it.

## Diagnose

<Steps>

1. Read the message of the failed step.

   ```sh
   kubectl -n pk-metal describe hostoperation reboot-w-1-x7k2p
   ```

2. Find the PodDisruptionBudgets that allow no disruption.

   ```sh
   kubectl --kubeconfig prod.kubeconfig get pdb -A
   ```

</Steps>

| Cause | Fix |
| --- | --- |
| A PodDisruptionBudget allows 0 disruptions | Scale the workload up, or change the budget. |
| A pod has an `emptyDir` volume | Move the pod. Or propose again with `--delete-emptydir-data`. You lose the data. |
| A pod does not stop in time | Propose the reboot again with a longer `--drain-timeout` or `--grace-period`. These are flags of [](cli:reboot), not of [](cli:retry). |

## Fix

Correct the cause first. Then find who made the operation. Its `spec.reason` tells you.

```sh
kubectl -n pk-metal get hostoperation reboot-w-1-x7k2p -o jsonpath='{.spec.reason}{"\n"}'
```

| Made by | Reason | Fix |
| --- | --- | --- |
| The operator, for a claim | `Provisioning`, `Release`, and others | Run `pk-metal retry pk-metal/reboot-w-1-x7k2p`. The operator proposes it again. A person approves it. |
| A person, with [](cli:reboot) | `Reboot` | `pk-metal retry` only deletes it. Then propose it again, for example `pk-metal reboot --drain-timeout 30m w-1`, and get it approved. |
| A rollout | `TalosRollout` | The rollout has failed. Follow [](rb:rollout-paused). |

To give the node back without the change, uncordon it:

```sh
kubectl --kubeconfig prod.kubeconfig uncordon w-1
```

<Callout type="caution">
Do not delete pods by force to make the drain pass. You can lose data of a stateful workload.
</Callout>

## Verify

A new operation for the node exists and goes past the drain step.

```sh
kubectl -n pk-metal get hostoperations
```
