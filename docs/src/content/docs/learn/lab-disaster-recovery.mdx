In this tutorial, the lab loses all etcd data of a cluster and gets it back from a snapshot.
The task [](lab:backup-restore) does the steps. You watch them and examine the result.

## Steps

### 1. Start a lab with one control plane

1. If a lab runs, stop it and delete the disks.

   ```sh
   mise run lab:down && mise run lab:reset
   ```

2. Start the lab and install the cluster.

   ```sh
   PK_LAB_NODES=1cp+0w mise run lab:up
   mise run lab:wait
   ```

<Checkpoint>
`lab:wait` ends with `converged after`. The cluster has one `Ready` node.
</Checkpoint>

### 2. Run the round

<Callout type="warning">
Do not run this task on a cluster that has data you must keep.
It wipes the etcd data of each control plane. You lose all changes after the snapshot.
</Callout>

1. Open the live view in a second terminal.

   ```sh
   mise run lab:top
   ```

2. Start the round in the first terminal.

   ```sh
   mise run lab:backup-restore
   ```

3. Follow the parts in the output.

<TermReplay src="casts/lab-backup-restore.json" caption="A replay with example data. The names of the snapshot and the operation are different in your lab." />

| Part in the output | What happens | Reference |
| --- | --- | --- |
| `etcd backup volume` | The manager gets a volume for snapshots. | [](ctrl:manager) |
| `EtcdBackupPolicy lab-dr, a snapshot, and markers around it` | The task makes an age key and a policy. It writes `dr-before`, takes a snapshot, and writes `dr-after`. | [](cli:backup) |
| `losing etcd` | `talosctl reset` wipes `EPHEMERAL` on the control plane. The TalosCluster reports `EtcdDataLost`. | [](kind:TalosCluster) |
| `restoring <snapshot>` | The user `lab-restorer` proposes the restore. The admin approves it. The task uploads the snapshot. | [](cli:restore) |
| `waiting for <operation> and for etcd` | The operation with [](act:EtcdRecover) runs. etcd starts from the snapshot. | [](kind:HostOperation) |

<Checkpoint>
The last line starts with `restored after` and ends with `dr-before is back, dr-after is not`.
</Checkpoint>

### 3. Examine the result

1. Show the ConfigMaps in the restored cluster.

   ```sh
   kubectl --kubeconfig .lab/workload.kubeconfig -n default get configmaps
   ```

   `dr-before` is in the list. `dr-after` is not.

2. Show the snapshots.

   ```sh
   metal/bin/pk-metal --kubeconfig .lab/kubeconfig backup list lab
   ```

3. Show the restore operation. Its phase is `Succeeded`.

   ```sh
   kubectl --kubeconfig .lab/kubeconfig -n pk-metal get hostoperations
   ```

4. Examine the files that the task kept.

   ```sh
   ls .lab/backup-restore/
   ```

   | File | Contents |
   | --- | --- |
   | `identity.txt` | The age identity. Only this key can decrypt the snapshot. |
   | `snapshot.db.age` | The encrypted snapshot |
   | `restorer.kubeconfig` | The kubeconfig of the user `lab-restorer` |

<Checkpoint>
The cluster is `Bootstrapped` again in `mise run lab:status`, and its node is `Ready`.
</Checkpoint>

If a step does not give its checkpoint, see [](lab:page/troubleshooting).

## What you learned

- The operator sees the loss of etcd data, and it does not bootstrap the cluster again without a person.
- A restore needs two persons and an approval, as each other change does: [](concept:approval).
- The operator stores only encrypted snapshots. You keep the key.
- A restore brings back the state of the snapshot. You lose later changes.
