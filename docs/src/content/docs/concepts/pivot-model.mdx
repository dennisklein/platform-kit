A pivot moves the operator and its state to another cluster, like `clusterctl move` in Cluster API.
All state is API objects, so the move is a copy of objects in a fixed sequence. No machine changes.

## What moves

- ConfigMaps and Secrets of the namespace `pk-metal`: the ledger, the BMC credentials, the secrets bundles, the rendered configs, the published credentials.
- All objects of `metal.pk.io` and `os.pk.io`, with their status, labels, annotations and finalizers.
- Finished operations too. They are the record of what was done to each machine.

## What does not move

Events, the leader lease, service account tokens, imager Jobs and the files in the media store.
The target builds missing installers again. The workload clusters do not move, because they do not depend on the operator.

## How the copy keeps objects correct

<dl>
  <dt>UIDs</dt>
  <dd>Each object gets a new UID. The move writes the new UID into `spec.claimRef.uid`, into the claim label of operations and into owner references.</dd>
  <dt>Identities</dt>
  <dd>The move writes each operation as its proposer and replays each approval as the person who gave it, so the admission policy accepts them.</dd>
  <dt>Status</dt>
  <dd>The move copies status under the name of the controller that owns each part. The hand-off record of a claim moves too, so no machine installs again.</dd>
  <dt>Markers</dt>
  <dd>Annotations on the namespace `pk-metal`: `pivoted-to` and `pivot-replicas` on the source, `pivot-source` on the target. They make a second run continue.</dd>
</dl>
