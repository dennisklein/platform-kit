After a pivot, the operator runs on machines that it manages.
A reboot of such a machine can stop the operator in the middle of an operation. So the operator holds these power actions.

## What is held

- A power cycle or power off of the node where the manager pod runs.
- A power cycle or power off of an installed control plane of the cluster of the operator. Installed means that the node answers now, or the claim records the hand-off.
- This covers an install, a release, a BIOS change and the executor itself.

The claim or the operation shows reason `SelfDisruption`.

## Terms

<dl>
  <dt>Own node</dt>
  <dd>The node in the environment variable `NODE_NAME` of the manager pod. The operator matches it to a [](kind:TalosNode) by name or address.</dd>
  <dt>allow-self-disruption</dt>
  <dd>The Host annotation `metal.pk.io/allow-self-disruption`. With it, the operator can take that machine down. The value is `<user name>: <reason>`. See [Named guard lifts](ref:audit-trail#named-guard-lifts).</dd>
</dl>

## With the annotation

A control plane still goes down only when:

1. no other control plane of the cluster reboots, and
2. the other control planes keep the etcd majority. The operator asks each of them over the Talos API at that moment. A control plane that does not answer in five seconds counts as down.

<Callout type="caution">
Remove `metal.pk.io/allow-self-disruption` when you complete the work.
The safer way is to move the operator to another cluster first, see [](flow:pivot).
</Callout>
