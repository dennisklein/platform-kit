A TalosRollout is one change to all nodes of a [](kind:TalosCluster): a Talos upgrade, a Kubernetes upgrade, a config change or a reboot.
One approval covers the full plan. The operator then changes one node at a time and checks the cluster between nodes.

## Kinds of rollout

| `spec.kind` | Change on each node | Reboot | Proposed by the operator when |
| --- | --- | --- | --- |
| `TalosUpgrade` | [](act:TalosUpgrade) to `target.talosVersion` | yes | a node runs another version than `spec.talosVersion` |
| `KubernetesUpgrade` | [](act:TalosApplyConfig) with the new kubelet and control-plane images | only if the node needs it | the API server reports another version than `spec.kubernetesVersion` |
| `Config` | [](act:TalosApplyConfig) with the current render | only if the node needs it | a node reports drift |
| `Reboot` | [](act:TalosReboot) | yes | never: you create it |

The operator checks these cases in this order and proposes only the first that applies.
While a rollout of the cluster is not finished, it proposes nothing new.
It does not propose a failed or aborted rollout again. Delete that rollout to get a new proposal.

## The plan

Before the approval, the operator writes the plan to `status.plan` on each pass:

1. Control planes, one at a time. The etcd leader goes last, so etcd elects a new leader only one time.
2. For a `KubernetesUpgrade`: one `KubeProxy` step that moves the kube-proxy DaemonSet to the new image.
3. Workers, at most `spec.maxUnavailableWorkers` at a time.

Each step names the node, its Host, the change (`from`, `to`), the pinned image or config digest, and the actions.
`status.planHash` is a sha256 over the cluster, the kind, the target, the drain policy and all steps.

The actions of a node step:

```text
drain → change → waitNodeReady → waitEtcdHealthy* → uncordon
```

`drain` and `uncordon` are only for a change that reboots the node. `waitEtcdHealthy` is only for a control plane.

## Run

<RollingUpgrade />

- **Approval.** The approver names the `planHash` that they saw. After the approval, the plan is frozen.
- **Plan changed.** If the plan that the operator would make now differs from the approved plan, the rollout ends with `Complete=False`, reason `PlanChanged`. Nothing runs.
- **Pause after the first node.** The rollout always stops after the first node. [](cli:rollout) `resume` sets `os.pk.io/resume` to the plan hash.
- **Health gate.** Before each step, the operator asks etcd and Kubernetes again. It needs a leader, no member with an error, no learner, all control planes as members and all other Nodes Ready. Until then, the reason is `WaitingForHealth`.
- **One rollout per cluster.** A second approved rollout waits until the first one ends.
- **Failure.** A step fails: the rollout stops with `RolloutFailed`. The steps that did not start are `Skipped`.

<Callout type="caution">
Do not abort a rollout to pause it. `spec.abort` cannot change back. Use `pk-metal rollout pause`, which sets `spec.paused`.
A node that runs finishes in both cases.
</Callout>

## Approval rules

A ValidatingAdmissionPolicy enforces the same rules as for a HostOperation:

1. The creator must name themselves in `spec.proposedBy`.
2. The approver is a person, never the operator. The approver is not the proposer if the site sets `selfApproval: Forbidden`.
3. `approvedBy` and `planHash` are set together, and cannot change after that.

Before each node operation starts, the [](ctrl:hostoperation) checks that this rollout still covers it.
If not, the operation fails with `RolloutRefused` and the machine does not change.

## Status

<FieldTable kind="TalosRollout" part="status" />

### Conditions

| Condition | Reasons |
| --- | --- |
| `Planned` | `PlanReady`, `PlanBlocked`, `NothingToDo` |
| `Approved` | `AwaitingApproval`, `PlanApproved`, `PlanChanged` |
| `Progressing` | `NotStarted`, `NodeRunning`, `WaitingForHealth`, `PausedAfterFirstNode`, `PausedByPerson`, `Succeeded`, `RolloutFailed`, `Aborted`, `PlanChanged` |
| `Paused` | `PausedAfterFirstNode`, `PausedByPerson`, `NotPaused` |
| `Complete` | `Succeeded`, `NothingToDo`, `RolloutFailed`, `Aborted`, `PlanChanged` |

Each step in `status.steps` is `Pending`, `Running`, `Succeeded`, `Failed` or `Skipped`.

`PlanChanged` means that the plan changed after a person approved it. Nothing ran. The rollout ends, and the operator proposes a new one.

## Example

```console
$ pk-metal upgrade talos lab v1.14.7
$ kubectl get talosrollouts
NAME                        CLUSTER   KIND           APPROVED   PROGRESS     COMPLETE   AGE
lab-talosupgrade-1a2b3c4d   lab       TalosUpgrade              NotStarted              1m
```

| Column | Shows |
| --- | --- |
| `APPROVED` | The name of the approver. Empty before the approval. |
| `PROGRESS` | The reason of the condition `Progressing`, for example `NodeRunning`. |
| `COMPLETE` | The status of the condition `Complete`: empty, `True` or `False`. |

[](cli:rollout) shows the plan and the state of each step.

A reboot of all nodes is a rollout that you write. `metal/config/samples/rollout-reboot.yaml` is an example.
