RBAC says who may create or patch an object. It cannot see the name that a person writes into a field.
Seven [ValidatingAdmissionPolicies](term:vap) close that gap. They are [CEL](term:cel) in the API server: no webhook, no certificate, no pod.

## At a glance

| Policy | Kind | Operations | Purpose |
| --- | --- | --- | --- |
| `hostoperation-approval` | [](kind:HostOperation) | CREATE, UPDATE | The approval gate of one operation. |
| `talosrollout-approval` | [](kind:TalosRollout) | CREATE, UPDATE | The approval gate of one rollout plan. |
| `hostclaim-provisioning` | [](kind:HostClaim) | CREATE, UPDATE | Who may choose the OS of a machine, and who may skip the boot approval. |
| `etcdbackuppolicy-guard` | [](kind:EtcdBackupPolicy) | CREATE, UPDATE | Who may choose who can read the etcd backups, and where they go. |
| `endpointprofile-guard` | [](kind:EndpointProfile) | CREATE, UPDATE | Who may change what the operator writes to the BMCs. |
| `taloscluster-credentials-guard` | [](kind:TalosCluster) | CREATE, UPDATE | Who may make the published admin credentials live longer than 24 hours. |
| `guard-lift` | HostOperation, HostClaim, [](kind:TalosNode) | CREATE, UPDATE | A guard lift names the person who sets it, and a reason. |

All seven have these settings:

<dl>
  <dt>`failurePolicy: Fail`</dt>
  <dd>If the API server cannot evaluate the policy, it refuses the request.</dd>
  <dt>`validationActions: [Deny]`</dt>
  <dd>A failed rule refuses the request with reason `Forbidden`.</dd>
  <dt>Parameters</dt>
  <dd>The ConfigMap `hostoperation-approval` in `pk-metal`. Key `operator` is the name of the manager. Key `adminGroup` is the admin group. Key `selfApproval` tells if a person can approve their own proposal.</dd>
  <dt>`parameterNotFoundAction: Deny`</dt>
  <dd>Without the ConfigMap, each create and update is refused. The gate fails closed.</dd>
</dl>

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: hostoperation-approval
  namespace: pk-metal
data:
  operator: system:serviceaccount:pk-metal:pk-metal-manager
  adminGroup: pk-metal:admins
  selfApproval: Allowed
```

## The `selfApproval` setting

The two approval policies read the key `selfApproval`. It applies to operations and to rollouts.

| Value | A person approves their own proposal | Use it when |
| --- | --- | --- |
| `Allowed` | Yes. The record names the same person as proposer and approver. | The team is too small for review by two persons. |
| `Forbidden` | No. Another person must approve. | One account must not change a machine alone. |
| Key not set | Yes, as `Allowed`. | |
| Another value | No, as `Forbidden`. The message tells you to set a correct value. | |

The operator never approves, with each value. [](howto:approval-permissions) tells you how to choose.

## `hostoperation-approval`

The CRD schema freezes the target, the actions, `approval.required` and `proposedBy`. The policy checks the rules that need the name of the requester.

| # | Rule | When | Message |
| --- | --- | --- | --- |
| 1 | Nobody creates an operation that is already approved. | CREATE | an operation cannot be created pre-approved |
| 2 | `spec.proposedBy` is your own name. | CREATE | spec.proposedBy must name you |
| 3 | Only the operator or an admin creates an operation with `approval.required: false`. | CREATE | only the operator or an admin may create an operation that needs no approval |
| 4 | An approval, once set, does not change. | UPDATE | approval is write-once |
| 5 | You approve as yourself: `approvedBy` is your name. | Approval write | you may only approve as yourself |
| 6 | The operator approves nothing. | Approval write | the operator approves nothing: a person with the pk-metal-approver role must approve |
| 7 | You approve your own proposal only if `selfApproval` is `Allowed` or not set. | Approval write | this site forbids approving your own proposal (selfApproval: Forbidden in ConfigMap pk-metal/hostoperation-approval): another person must approve |

<dl>
  <dt>Why rule 3</dt>
  <dd>Anybody else could skip the gate. The operator itself creates such operations in three cases. These are the node steps of an approved rollout, an install of a claim with `provisioning.approval: Automatic`, and a release that needs no person.</dd>
  <dt>Why rule 6 names the operator</dt>
  <dd>The operator proposes most operations. A person must approve them. RBAC also stops the operator: it has no `patch` on operations. See [](ref:rbac). Rule 6 is the second lock. It is the same rule as rule 5 of `talosrollout-approval`. No setting changes it.</dd>
  <dt>Why rule 7 is a setting</dt>
  <dd>A small team cannot always find a second person. With `Allowed`, the record still names who proposed and who approved. A value that is not `Allowed` or `Forbidden` closes the gate. The message names the value.</dd>
</dl>

Example: the manager proposed an operation. `jo` approves it.

```sh
kubectl -n pk-metal patch hostoperation install-node-07 --type merge \
  -p '{"spec":{"approval":{"approvedBy":"jo"}}}'
```

The policy accepts this only if the username of `jo` is `jo`. Use [](cli:approve). It writes your name.

## `talosrollout-approval`

One approval covers each node of a rollout plan. So the rules are the rules of an operation, plus the plan hash.

| # | Rule | When | Message |
| --- | --- | --- | --- |
| 1 | Nobody creates a rollout with `approvedBy` or `planHash`. | CREATE | a rollout cannot be created pre-approved |
| 2 | `spec.proposedBy` is your own name. | CREATE | spec.proposedBy must name you |
| 3 | `approvedBy` and `planHash`, once set, do not change. | UPDATE | approval is write-once |
| 4 | You approve as yourself. | Approval write | you may only approve as yourself |
| 5 | The operator approves nothing. | Approval write | the operator approves nothing: a person with the pk-metal-approver role must approve |
| 6 | You approve your own proposal only if `selfApproval` is `Allowed` or not set. | Approval write | this site forbids approving your own proposal (selfApproval: Forbidden in ConfigMap pk-metal/hostoperation-approval): another person must approve |

The approval names the `planHash` that you read. The [](ctrl:talosrollout) runs the rollout only while that hash is the plan.

## `hostclaim-provisioning`

A claim that names a [](kind:TalosNode) makes the operator mount the config of that node on the machine. A control-plane config carries the CA keys of the cluster. So these changes are an admin decision.

| # | Rule | When | Message |
| --- | --- | --- | --- |
| 1 | Only an admin sets or changes `spec.os.nodeRef`. | CREATE, UPDATE | only an admin may name the TalosNode a claim boots |
| 2 | Only an admin turns `spec.provisioning.approval` to `Automatic`. | CREATE, UPDATE | only an admin may waive provisioning approval |
| 3 | Only an admin points a claim at another machine: a change of `spec.assetRef` or `spec.systemRef`. | UPDATE | only an admin may point a claim at another machine |

- A value that did not change passes. So the finalizers of the operator and edits to other fields need no admin.
- Each refusal says who you are, your groups, and where group membership comes from.

<Callout type="caution">
Cluster admin (`system:masters`) is not enough. The policy asks for the group `pk-metal:admins` by name.
A ClusterRoleBinding does not make you a member of a group. Your credential does. See [Get into the admin group](ref:rbac#get-into-the-admin-group).
</Callout>

## `etcdbackuppolicy-guard`

A snapshot holds each Secret of the cluster. The age recipients decide who can decrypt it. The sink decides where the ciphertext goes. A person who adds a recipient can read each later snapshot. So these changes are an admin decision.

| # | Rule | When | Message |
| --- | --- | --- | --- |
| 1 | Only an admin creates a backup policy, or changes `spec.encryption` or `spec.sink`. | CREATE, UPDATE | only an admin may create a backup policy or change its encryption or sink |

- The sink includes the S3 endpoint, the bucket, `credentialsSecretRef` and `caSecretRef`.
- `spec.interval`, `spec.retention` and `spec.suspend` need no admin.
- The CRD schema refuses an `http://` S3 endpoint unless [`allowPlainHTTP`](kind:EtcdBackupPolicy#spec.sink.s3.allowPlainHTTP) is `true`. Set it only for a store in a lab.

## `endpointprofile-guard`

An [](kind:EndpointProfile) has no approval of its own. The operator applies it to each BMC that it selects. It makes an Administrator account, sets the NTP servers, and replaces the TLS identity, which restarts the BMC.

| # | Rule | When | Message |
| --- | --- | --- | --- |
| 1 | Only an admin creates a profile or changes its `spec`. | CREATE, UPDATE | only an admin may create or change an EndpointProfile |

Labels and annotations of a profile need no admin.

## `taloscluster-credentials-guard`

`spec.credentials.ttl` of a [](kind:TalosCluster) sets how long the published admin kubeconfig and talosconfig are valid. Nobody can revoke a copy before it expires. The CRD allows 720 hours at most.

| # | Rule | When | Message |
| --- | --- | --- | --- |
| 1 | Only an admin sets `spec.credentials.ttl` to more than 24 hours. | CREATE, UPDATE, when the value changes | only an admin may set spec.credentials.ttl above 24h |

Each person who can patch a cluster can make the time shorter, or remove it. The on-call and approver roles can patch clusters.

## `guard-lift`

Three annotations lift a safety rule of the operator: `metal.pk.io/override-cluster-guard`, `metal.pk.io/ignore-window` and `metal.pk.io/ack-etcd-risk`. RBAC lets each holder of `patch` set them. This policy makes the value name that holder.

| # | Rule | When | Message |
| --- | --- | --- | --- |
| 1 | A request that sets a lift, or changes its value, gives the value `<username>: <reason>`. The username is the username of the request. The reason is not empty. | CREATE, UPDATE | `a guard lift must name you and say why: set … to "<username>: <reason>"` |

- A request that removes a lift passes. That puts the rule back.
- A request that leaves the value as it is passes. So the writes of the operator and a value from before the policy pass.
- The operator sets none of these annotations, so it has no exemption.
- A GitOps controller that applies a lift must name its own identity. The commit names the person.
- See [](ref:audit-trail) for the records that show the lift.
