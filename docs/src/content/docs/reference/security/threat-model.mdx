pk-metal can wipe disks, flash firmware and boot any image on a machine. This page names what an attacker could want, where the secrets go, and what stops misuse.

| # | Crossing | What crosses | Control |
| --- | --- | --- | --- |
| 1 | Person to API server | Approvals | RBAC and the [](ref:admission-policies). A person proposes, and a person approves as themselves. The site setting `selfApproval` decides if that can be the same person. The operator never approves. Two identities can create work that needs no approval: the operator service account and a member of the admin group. See [Who can skip the gate](#who-can-skip-the-gate). |
| 2 | Manager or CLI to BMC | BMC login, power and boot commands | Redfish over TLS. Each [](kind:ManagementEndpoint) has its own `spec.tls`, see [BMC certificates](#bmc-certificates). The CLI checks the BMC certificate against `--bmc-ca`; `--insecure` turns the check off and prints a warning. |
| 3 | BMC to media service | Each boot medium, maybe with a node config | HTTPS that the BMC does not verify. A grant token in the URL, bound to the first source address. A user and password for each grant that carries a secret. The digest of each medium. A NetworkPolicy for the BMC network. See [Media grants](#media-grants). |
| 4 | Manager to node | Talos API calls | Mutual TLS with the cluster certificates. To observe a node, the manager can also call the maintenance service without authentication. That call reads the version only. It sends no configuration. |
| 5 | Manager to sink | Etcd snapshots | Age encryption to public recipients. Only the holder of the age identity can decrypt, on their own machine. Only an admin chooses the recipients and the sink. |
| 6 | Manager to BMC, from an [](kind:EndpointProfile) | Account, NTP servers, TLS identity | No operation and no approval: the profile is the approval. Only an admin creates or changes a profile (`endpointprofile-guard`). |

## Assets worth protecting

<dl>
  <dt>BMC logins</dt>
  <dd>Secrets in `pk-metal`. With them, a person controls power and boot of a machine outside Kubernetes.</dd>
  <dt>Rendered node configs</dt>
  <dd>A control-plane config carries the CA keys of the cluster. It leaves the manager only on a config ISO or an embedded installer, and only under a grant.</dd>
  <dt>Cluster credentials</dt>
  <dd>The admin talosconfig and kubeconfig of each cluster, in Secrets in `pk-metal`.</dd>
  <dt>Etcd snapshots</dt>
  <dd>The full state of a cluster, including its Secrets.</dd>
  <dt>The approval gate</dt>
  <dd>A bypass lets one identity wipe or reboot machines alone. The operator service account and the admin group can bypass it by design today. Protect both as you protect the gate. With `selfApproval: Allowed`, one person who can propose and approve can also change a machine alone. See [Known limits](#known-limits).</dd>
  <dt>The operator service account</dt>
  <dd>Its token can create an operation with `approval.required: false`, with any actions. The executor runs it with no person. The operator code decides when it does this: the node steps of an approved rollout, an install with `provisioning.approval: Automatic`, and a release that needs no person. Admission does not limit the actions.</dd>
  <dt>The admin group</dt>
  <dd>A member can create an operation that needs no approval. A member can also set a claim to `Automatic`, name the TalosNode of a claim, change the backup recipients, and change an EndpointProfile. One member can do these alone. Keep the group small, and audit each create with `approval.required: false` by a person. See [Get into the admin group](ref:rbac#get-into-the-admin-group).</dd>
  <dt>Data at rest</dt>
  <dd>Rendered configs, BMC logins, the secrets bundle of each cluster, the published credentials and the S3 keys are Kubernetes Secrets. They are plain text in etcd unless the management cluster encrypts Secrets at rest. Set encryption at rest to on. Embedded installers that carry a node config stay on the volume of the [media store](term:media-service) until the install ends or fails. Then the operator deletes them, and the config ISO Secrets too. A delete is an unlink: the data can stay on the disk. Use an encrypted StorageClass for it.</dd>
</dl>

### Who can skip the gate

| Identity | What it can do alone | What checks it |
| --- | --- | --- |
| Operator service account | Create an operation that needs no approval. It cannot approve an operation or a rollout, with each `selfApproval` value. | RBAC (no `patch`) and rule 6 of `hostoperation-approval` |
| Admin group | Create an operation that needs no approval, and the other admin changes above. | `hostoperation-approval`, `hostclaim-provisioning`, `etcdbackuppolicy-guard`, `endpointprofile-guard` |
| A person with `create` and `patch` on operations or rollouts, if `selfApproval` is `Allowed` | Propose a change and approve it. The record names the person as proposer and as approver. | Rule 7 of `hostoperation-approval`, rule 6 of `talosrollout-approval`, and the `selfApproved` field of the [](ref:audit-trail) |
| Holder of `patch` on operations | Lift a maintenance window or the cluster guard on an operation that a person approved. The value must name the person and a reason. | RBAC, `guard-lift`, and the [](ref:audit-trail) |

### Known limits

<dl>
  <dt>Self-approval</dt>
  <dd>The default of `selfApproval` is `Allowed`. Then one person with propose and approve rights can change a machine alone. The record still names them in `spec.proposedBy` and in `spec.approval.approvedBy`. If one account must not change a machine alone, set `Forbidden`. See [](howto:approval-permissions).</dd>
  <dt>Operator work without approval</dt>
  <dd>The identity of the operator can create operations that need no approval. These are the node steps of an approved rollout, an install of a claim with `provisioning.approval: Automatic`, and a release that needs no person. `selfApproval: Forbidden` does not change this. Admission does not limit the actions of these operations. Protect the token of the operator service account: give nobody `impersonate` on it, or `create` on `serviceaccounts/token` in `pk-metal`, and do not copy its token out of the cluster.</dd>
</dl>

## Controls

### Media grants

The BMC downloads each boot medium from the [media service](term:media-service), also the factory installer and an `imageUrl`. The operator downloads those first, over TLS that it verifies, and checks their digest. A BMC never fetches from another server.
The BMC does not check the certificate of the media service. Thus HTTPS protects against a passive listener only, not against a machine in the middle on the BMC network. The approval plan says "certificate not verified by the BMC".

1. Each download needs a [grant](term:grant): a 128-bit random token in the URL path.
2. A grant for a medium that carries a secret also has its own user and password for HTTP Basic authentication. The media service compares them in constant time.
3. A grant serves one artifact for one operation. The executor checks the artifact digest against the approved digest.
4. The first source address that fetches through a grant owns it. The media service refuses the grant to each other address.
5. Each refusal gets the same answer, `401`. A client cannot tell a wrong token from an expired grant.
6. The [](ref:audit-trail) gets each first fetch, each refusal of a known grant and the end of each grant. A line has the source address and the bytes, never the token.
7. A grant ends after a limited time: 15 minutes plus the power and check-in timeouts of the operation. That is often 45 minutes or more. Until then, the BMC can download the artifact more than one time.
8. The executor revokes the grant when the operation ends or is deleted. A failed step ejects the media that the operation mounted, and the message records the result.
9. Grants live in memory only. A restart of the manager forgets them, so it fails closed. A mount that runs gets a new grant on retry.
10. The BMC network must be an isolated L2 island. The confidentiality of a node config rests on the grant and on that island.
11. An `imageUrl` needs `https://` and a digest. Thus an operation cannot boot an arbitrary image that nobody checked.

The media Service is a NodePort (30443). It listens on each node of the management cluster, not only on the BMC island. The base install has a NetworkPolicy that lets only the BMC network in; set that network in your overlay. A NodePort with `externalTrafficPolicy: Cluster` can replace the BMC address with a node address (SNAT). Then the policy and the source binding see the node, and protect less. See [](ref:media-store#source-addresses-and-nat).

On Huawei iBMC, the user and password of the grant go into the image URL. The BMC stores that URL, so a read-only BMC user can see them until the grant ends. An installer grant has no credentials, so its URL holds none. A BMC error often repeats the URL. The operator masks the credentials and the grant token in each error text. It does this before it writes the text to a status, an Event, a log line or the [](ref:audit-trail).

### BMC certificates

The manager checks the certificate of a BMC with one of three sources:

1. The `spec.tls` of the [](kind:ManagementEndpoint): a CA Secret, or `insecureSkipVerify`. The manager copies its own default into it when it makes the endpoint from an Asset.
2. The manager default: the CA of `--bmc-ca-secret`, else `--bmc-insecure`, else the system CAs.
3. An [](kind:EndpointProfile) with `spec.tls` replaces the certificate of the BMC with one from the issuer that it names.

`pk-metal` on a workstation ([](cli:check), [](cli:inventory), [](cli:boot)) checks the BMC certificate against the CA file of `--bmc-ca`, else the system CAs. `--insecure` turns the check off.

Watch `ManagementEndpoint.spec.tls` and `EndpointProfile.spec.tls`. A change there changes whom the manager trusts, and whom it sends the BMC login to.

### Relay

The [relay](concept:relay) lets the CLI drive a BMC through a jump host on day 0.

- Each request line carries HMAC-SHA256 over a new 128-bit nonce, the verb and the argument. The key is a shared secret of 32 characters or more, from a file or `$PK_METAL_RELAY_SECRET`.
- The HMAC authenticates. It does not encrypt. So the relay listens on loopback only, and you reach it through `ssh -L`.
- The operator does not use the relay. It is a day-0 tool.

### Etcd backups

- The operator holds only the public age recipients. It can write a backup but cannot read one.
- A restore decrypts on the machine of the person who holds the age identity. Then the person uploads the snapshot with [](cli:restore).
- `pk-metal-backup` holds no Secret.

### Credentials

- Published cluster credentials live 24 hours by default, and 720 hours at most. The operator renews them when one third of the time is left.
- [](cli:render) writes credentials that live 24 hours by default, and 720 hours at most.
- `readerTalosconfig` publishes a talosconfig with the `os:reader` role only.
- The client certificate for the install check-in lives 10 minutes.
- The metric `pk_metal_credentials_expiry_timestamp_seconds` shows each expiry.

### Self and cluster guards

The operator refuses actions that would take down the cluster that it runs on, or break etcd quorum of a workload cluster. See [](ctrl:protection).

## What this model does not cover

- A person with cluster admin can change the policies, the ConfigMap or the RBAC. Watch those objects in the kube-apiserver audit log. See [](ref:audit-trail).
- A BMC with known default logins. Change them before enrollment.
- A node that answers on the maintenance service. The manager reports it as `MaintenanceMode`, but a machine on the node network can pose as it. Take `MaintenanceMode` as a hint, not as proof.
- The firmware that you flash. The operator checks the digest that you approved, not who built the image.

<Callout type="caution">
Do not set `--bmc-insecure` outside a lab. It accepts any BMC certificate, so a machine on the BMC network can pose as a BMC and receive its login.
</Callout>
