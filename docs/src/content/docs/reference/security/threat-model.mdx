pk-metal can wipe disks, flash firmware and boot any image on a machine. This page names what an attacker could want, where the secrets go, and what stops misuse.

## Assets worth protecting

<dl>
  <dt>BMC logins</dt>
  <dd>Secrets in `pk-metal`. With them, a person controls power and boot of a machine outside Kubernetes.</dd>
  <dt>Rendered node configs</dt>
  <dd>A control-plane config carries the CA keys of the cluster. It leaves the manager only on a config ISO or an embedded installer, and only under a grant.</dd>
  <dt>Cluster credentials</dt>
  <dd>The admin talosconfig and kubeconfig of each cluster, in Secrets in `pk-metal`.</dd>
  <dt>Etcd snapshots</dt>
  <dd>The full state of a cluster, including its Secrets.</dd>
  <dt>The approval gate</dt>
  <dd>A bypass would let the operator, or one person, wipe or reboot machines alone.</dd>
</dl>

## Controls

### Media grants

The BMC downloads boot media from the [media service](term:media-service). The BMC does not check the certificate, so HTTPS gives privacy but no identity.

1. Each download needs a [grant](term:grant): a 128-bit random token in the URL path.
2. A grant serves one artifact for one operation. The executor checks the artifact digest against the approved digest.
3. A grant ends after a limited time: 15 minutes plus the power and check-in timeouts of the operation.
4. The executor revokes the grant when the operation ends or is deleted.
5. Grants live in memory only. A restart of the manager forgets them, so it fails closed. A mount that runs gets a new grant on retry.
6. The BMC network must be an isolated L2 island. The confidentiality of a node config rests on the grant and on that island.

### Relay

The [relay](concept:relay) lets the CLI drive a BMC through a jump host on day 0.

- Each request line carries HMAC-SHA256 over a new 128-bit nonce, the verb and the argument. The key is a shared secret of 32 characters or more, from a file or `$PK_METAL_RELAY_SECRET`.
- The HMAC authenticates. It does not encrypt. So the relay listens on loopback only, and you reach it through `ssh -L`.
- The operator does not use the relay. It is a day-0 tool.

### Etcd backups

- The operator holds only the public age recipients. It can write a backup but cannot read one.
- A restore decrypts on the machine of the person who holds the age identity. Then the person uploads the snapshot with [](cli:restore).
- `pk-metal-backup` holds no Secret.

### Credentials

- Published cluster credentials live 24 hours by default. The operator renews them when one third of the time is left.
- `readerTalosconfig` publishes a talosconfig with the `os:reader` role only.
- The client certificate for the install check-in lives 10 minutes.
- The metric `pk_metal_credentials_expiry_timestamp_seconds` shows each expiry.

### Self and cluster guards

The operator refuses actions that would take down the cluster that it runs on, or break etcd quorum of a workload cluster. See [](ctrl:protection).

## What this model does not cover

- A person with cluster admin can change the policies, the ConfigMap or the RBAC. Watch those objects.
- A BMC with known default logins. Change them before enrolment.
- The firmware that you flash. The operator checks the digest that you approved, not who built the image.

<Callout type="caution">
Do not set `--bmc-insecure` outside a lab. It accepts any BMC certificate, so a machine on the BMC network can pose as a BMC and receive its login.
</Callout>
