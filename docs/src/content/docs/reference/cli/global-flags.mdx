Two flags select the cluster that a command talks to.
They follow the rules of `kubectl`.

## Where to put them

Put the global flags before the command or after it. The two forms are equal.
The flags of a command can also come after its arguments. After `--`, each word is an argument.

<Terminal
title="global flags"
text={`
    $ pk-metal --context kind-pk-metal status
    $ pk-metal status --context kind-pk-metal
    $ pk-metal --kubeconfig .lab/kubeconfig top
`}
/>

## Commands that accept them

All commands that talk to the Kubernetes API accept the global flags:

- [](cli:status) and [](cli:top)
- [](cli:approve), [](cli:retry), [](cli:abort), [](cli:hold), [](cli:unhold) and [](cli:rollout)
- [](cli:reboot), [](cli:upgrade), [](cli:scale), [](cli:reinstall), [](cli:replace) and [](cli:wipe)
- [](cli:backup) and [](cli:restore)
- [](cli:pivot)

These commands do not talk to the Kubernetes API, and they refuse the global flags after the command:
[](cli:check), [](cli:inventory), [](cli:render), [](cli:boot), [](cli:bootstrap), [](cli:relay), [](cli:sim) and [](cli:version).

<Callout type="note">
Give [](cli:pivot) the source cluster with the global flags. Give it the target cluster with `--to` and `--to-context`.
</Callout>

## Other inputs

Some commands read a secret from the environment. A secret is never a flag, so it does not show in the process list.

| Variable | Used by | Content |
| --- | --- | --- |
| `KUBECONFIG` | All commands that talk to the cluster | The kubeconfig file, when [`--kubeconfig`](cli:global-flags#--kubeconfig) is not set. |
| `PK_METAL_BMC_PASSWORD` | [](cli:check), [](cli:inventory), [](cli:boot) | The password of the BMC user. |
| `PK_METAL_RELAY_SECRET` | [](cli:relay), [](cli:boot) | The shared secret of the relay. |
