The workflow `lab-e2e` runs the virtual lab on a hosted runner.
It uses the same tasks as you do. [](lab:wait) does the approval, through the same [](cli:approve) that a person uses.

## At a glance

## When each round runs

| Round | Push to `claude/**` | Every night | By hand |
| --- | --- | --- | --- |
| Install and release (job `lab`) | Yes | Yes | Yes |
| `day2` | No | Yes | With its input |
| `observe` | No | Yes | With its input |
| `upgrade` | No | Yes | With its input |
| `backup_restore` | No | Yes | With its input |
| `scale` | No | Yes | With its input |
| `pivot` | No | Yes | With its input |
| `huawei` fleet | No | No | With its input |

The nightly run starts at 02:17 UTC. GitHub starts it on the default branch only.
The input `huawei` changes the fleet, not the rounds. Thus the nightly run does not use it.

1. The job gives the runner user access to KVM. It installs QEMU and OVMF.
2. `mise run lab:doctor` checks the runner.
3. `mise run lab:up` starts the lab.
4. `mise run lab:wait` approves the installs and waits for three Provisioned Hosts and three Ready nodes.
5. `mise run lab:status` and `mise run lab:kubeconfig` show the result.
6. `mise run lab:release default/node-3` releases one machine and waits until its Host is Available.

## Inputs

| Input | Job | What it adds |
| --- | --- | --- |
| `huawei` | `lab` | `node-2` gets a [one-slot BMC](lab:page/simulated-bmc#one-slot-bmc). The operator builds an installer for it. |
| `day2` | `lab` | [](lab:day2) before the release: two reboots and a Config rollout without a reboot. |
| `observe` | `lab` | [](lab:observe) after the install: status tables, metrics and a maintenance window. |
| `upgrade` | `upgrade` | A lab that starts on Talos `v1.14.5`, then [](lab:upgrade). |
| `backup_restore` | `backup-restore` | A lab with one machine, then [](lab:backup-restore). |
| `scale` | `scale` | A lab with five machines, then [](lab:scale). |
| `pivot` | `pivot` | Two clusters with one machine each, then [](lab:pivot). |

## Jobs

| Job | Size | Environment | Time limit |
| --- | --- | --- | --- |
| `lab` | `1cp+2w` (default) | `PK_LAB_RELEASE_TIMEOUT=600` | 75 minutes. 85 with `observe`, 135 with `day2`, 145 with both and at night. |
| `pivot` | `1cp+0w` and `1cp+0w` | `PK_LAB_NODES`, `PK_LAB_WORKLOAD` | 90 minutes |
| `backup-restore` | `1cp+0w` | `PK_LAB_NODES` | 90 minutes |
| `scale` | `3cp+2w` | `PK_LAB_NODES`, a spec with 2560 MiB for each control plane | 150 minutes |
| `upgrade` | `1cp+1w` | `PK_LAB_TALOS=v1.14.5`, `PK_LAB_ROLLOUT_TIMEOUT=3000` | 120 minutes |

All jobs set `PK_LAB_MIN_FREE_GIB=10` and `PK_LAB_WAIT_TIMEOUT=2400`.
A hosted runner has 4 cores and 16 GB of memory. The `lab:up` step takes about four minutes, and the three installs take about three minutes more.

## Start a run by hand

1. Open the **Actions** tab of the repository.
2. Select the workflow **lab-e2e**.
3. Select **Run workflow** and the branch.
4. Select the inputs that you want.
5. Select **Run workflow**.

With the `gh` command:

```sh
gh workflow run lab-e2e --ref <branch> -f day2=true -f observe=true
```

## Diagnostics

On a failed or canceled run, each job runs [](lab:collect) and uploads the result.

| Job | Artifact |
| --- | --- |
| `lab` | `lab-diagnostics` |
| `pivot` | `lab-pivot-diagnostics` |
| `backup-restore` | `lab-backup-restore-diagnostics` |
| `scale` | `lab-scale-diagnostics` |
| `upgrade` | `lab-upgrade-diagnostics` |

The files are in [diagnostics](lab:page/troubleshooting#diagnostics).
