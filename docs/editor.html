platform-kit · editor design

The generic editor

The design says one sentence about the editor: "It edits any repo file through a schema-driven form, on all layers." This document reviews that promise against the design and the demo code, and makes it into a contract: one field address, one set of edit operations, one write-rule table, one check pipeline and one form model. Web UI, CLI, MCP agents, chat and the sync bot all use it.

Part of design.html §9 · Related: work kinds and progress reports · Evidence: the demo code of the design talk

Summary

Five review lenses read the design and the demo code. A skeptic checked each lens against the sources. They found 50 issues. The skeptics dropped none, but corrected 46 refinements that were too heavy or wrong. After merging duplicates, 35 findings remain. 19 are high. Four of them can corrupt data or break a cluster today:

  • Secrets are restored by position. Delete a list item above a masked secret, and the save writes the wrong ciphertext into the wrong item. No error shows.
  • Edits to SOPS files skip SOPS. The SOPS MAC covers all values. A change to a plain field such as spec.interval makes Flux decryption fail after merge.
  • A conflict discards the human's edits. When an agent writes the open file, the next autosave gets 409. The only way out is "Reload", which throws the buffer away.
  • Undo can silently revert an agent. An agent write lands in the CodeMirror history. Ctrl+Z reverts it and autosave stores the revert with a valid base.

The refined design has five parts. Each one closes a group of findings:

One field addressFile, document selector and a field path with quoted keys and keyed list selectors. Problems, deep links, suggestions, secrets and diffs all use it.
One edit engineEdit operations with expect and baseSha. The bench is the only structural YAML writer. It keeps bytes outside the touched node.
One write-rule tableTruth class, field source, secret and path rights decide each write. The bench enforces it for every caller, and CI runs the same check.
Secrets with identityMasks carry a hash of their ciphertext. SOPS writes keep the MAC valid, with or without the key. Only people set secret values.
A form that is never lossyEvery key of a file is reachable from the form. Unknown keys, free subtrees and absent fields have a place. Each read-only field says why.

The editor at a glance

Six surfaces write repo files. Today they use four write dialects. In the refined design they all send the same edit operations to the bench. The bench is the only place that turns an operation into bytes.

Steps 1 to 5 run for every write, whoever sends it. The YAML view sends full text; the bench parses it into the same tree, so steps 2, 4 and 5 still apply.

1The field address

Problems, deep links, edit operations, suggestions, secrets, conflict rows, the source map and semantic diff lines all point at a field. Today each one uses a dotted string that breaks on real Kubernetes keys. The refined design has one address.

Rule A1 · grammar path = seg { seg }; seg = "." ident | '["' key '"]' | "[" N "]" | "[" keyfield "=" value "]". An ident is [A-Za-z_][A-Za-z0-9_-]*. A key with any other character uses the quoted form. The first segment has no dot. Go implements the grammar once; the TypeScript client gets the same parser from shared golden tests (dots, slashes, digits, empty keys, quotes).
Rule A2 · canonical form Where the schema declares a list key (x-pk-list.key, or x-kubernetes-list-map-keys in a CRD), the canonical form uses the keyed selector [name=p2]. An index is canonical only in a list without a key. The bench accepts both forms on input and always answers with the canonical form.
Rule A3 · stability An index path is valid only together with a matching baseSha. Anything stored and applied later (suggestions, conflict replay, bulk edits, undo entries) uses the canonical form plus expect.
Rule A4 · documents Kind detection, schema, problems and edits work per document. The selector is kind/name (namespace added when two documents share it) or the index for a document without a kind. In a file with one document the selector is optional.

The REST API drops the implicit spec. shortcut. pk edit may keep it as input sugar, but it prints the resolved path. The dotted label "spec.ports[name=p2].peer.port" is also the display text in the form, problems and diffs.

2Kinds and the effective schema

2.1 Identity and matching

A kind is identified by (group, kind). A schema is identified by (group, kind, version). Every API path and every x-pk-ref uses group/kind, so Flux Kustomization and kustomize Kustomization no longer collide.

The registry matches each document in this order:

StepQuestionResult
1Which role has the file in the kustomization graph? The renderer already builds this graph.resource → step 2. patch → schema of the patch target with every required removed. generator input or Helm values file → chart values schema (2.4). plain → step 2.
2Does the document have apiVersion and kind?Own kind or third-party kind of that group, kind and version. An unknown version of a third-party kind gives a warning and YAML-only editing, not an error.
3No apiVersion? Do the path rules of a kind match?For example control/talos/*/talconfig.yaml or Markdown front matter under kb/. The kb special case moves from repo.go into the Article kind's match rule.
4Nothing matches.No kind: YAML editor only, still with masking, the redactor and secret checks.

The path list of an own kind is the default location for new files. A file of that kind at another path gets a warning, not an error (decision D6).

2.2 One effective schema, one walker

When the bench registers a kind, one Go pass stamps the effective values on every schema node. After this pass every walker reads only the node it is on. The existing schema endpoint serves the effective schema, so no new endpoint is needed.

  • x-pk-truth and x-pk-source: nearest ancestor, then the kind default, then intent / git.
  • x-pk-secret: always inherits down. Everything under a secret object is secret.
  • x-pk-ui: does not inherit, except group.

One Go walker, schema.At(schema, path), follows properties, items, additionalProperties, patternProperties, $ref/$defs and allOf. It resolves oneOf/anyOf only through a declared discriminator. Masking, entity pages, the LLM redactor (by exact path, not by leaf key name), sync and pk check all use it.

Schema generation moves to $defs plus $ref for named structs, with a visited set. A recursive type then works and can never crash the bench. A registration test generates the schema of every kind with a timeout.

2.4 Third-party schemas and Helm values

  • Third-party schemas are the upstream CRD files, vendored into platform-kit for each supported version by a make target. When the repo itself holds the CRD at its pinned version (for example Flux gotk-components.yaml), the editor prefers that copy.
  • Overlays only add x-pk hints (path pattern → ui, secret, ref). They never add validation the CRD does not have. The demo subsets with additionalProperties: false go away.
  • Helm value hints are keyed by chart name. The editor uses the chart's values.schema.json when it exists, plus an optional overlay. They apply only to a HelmRelease that names that chart, and to its valuesFrom files.
  • Kubernetes extensions map to the form: x-kubernetes-int-or-string → int-or-string widget; x-kubernetes-preserve-unknown-fields → embedded YAML block; x-kubernetes-list-map-keys → x-pk-list.key.

2.5 One schema set for bench and CI

Kinds are compiled into platform-kit, and every admin runs a bench on a laptop. The repo pins the platform-kit version in .pk/platform-kit.yaml. CI uses the pinned version. A bench of another version shows a banner and refuses commit and "mark ready" until it matches. Each problem carries the platform-kit version that found it.

3Edit operations

An edit is a list of operations on one file, or a batch over many files. Web form, pk edit, MCP and accepted suggestions all use it. The YAML view and Markdown bodies send full text; the bench parses that text and applies the same rules.

# one file
PATCH /changes/{id}/files/{path}
{ "baseSha": "9f2c1e0",
  "doc": "Node/cn-035",
  "ops": [
    { "op": "set",    "field": "spec.ports[name=p2].peer.port", "value": 38, "expect": 37 },

{ "sha": "41b7a2d", "content": "<masked>",

  "problems": [ … fast checks for this file … ],
  "renderSeq": 118 }

# many files, all or nothing, one render, one event

Rule O1 · preconditionEvery write carries baseSha, or every op carries expect. A write without both gets 428 for every caller. A new file uses the empty-blob sha. Delete and move need baseSha too.
Rule O2 · atomicOps apply in list order. If one op fails a rule, the bench writes nothing and answers 422 with the op index and the reason.
Rule O3 · one writer of bytesThe bench CST splicer is the only structural YAML writer. Its byte rules:
  • Bytes outside the touched node stay identical. A document that no op touches is never re-encoded.
  • A scalar edit keeps its quoting style. A new key goes to its schema position with the indentation of its siblings. A new list item copies the block or flow style of its siblings.
  • An edit through a YAML alias is refused with a pointer to the anchor.
  • Test corpus: representative seed files (multi-doc, flow lists, comments, SOPS). A no-op round trip is byte-identical. A one-scalar edit changes one line.

The form shows the new value at once (optimistic), sends the ops with the 750 ms autosave, and then adopts the bytes and sha from the answer. On a laptop the round trip costs tens of milliseconds, so the TypeScript splicer can go (decision D4). The answer carries the fast checks; the render runs after the write and arrives as render.updated {renderSeq}. A save never waits for a render.

5Concurrent edits, undo and commit

One worktree has many writers: the browser autosave, other tabs, the MCP agent, chat accept, a sync pull and a rebase. There is no lock service, and the design keeps it so. Field-level expect lets two writers meet without losing work. The video shows the main case in under 80 seconds.

If the video does not load, open editor-concurrent-edits.mp4 next to this file. Explainer: an agent and a person change the same file. The old flow loses the person's edit. The new flow replays the edit by field, and shows a conflict only where both changed the same field.

Rule C1 · one writer at a time per worktreeThe bench runs write, commit, rebase, pull and restore for one worktree under one in-process mutex, and re-checks the base inside it. This is not a lock service: it holds no state between requests.
Rule C2 · re-apply by fieldA write with an old baseSha is applied to the current file when every op's expect still holds. The answer is 200 {sha, rebased: true}. Otherwise the answer is 409 {conflicts: [{field, base, mine, theirs}], currentSha, changedBy, origin} and nothing is written.
Rule C3 · never discard a bufferThe form keeps unsaved edits as ops. On 409 or change.updated it fetches the file and replays the ops. A conflicting field becomes a conflict row with Keep mine and Take theirs. In YAML mode the editor tries a three-way text merge; if that fails it shows theirs and mine side by side, with Overwrite with mine as a confirmed write on the new base.
Rule C4 · say who changed the filechange.updated carries {path, sha, by, origin: agent | chat | sync | rebase | tab} and the applied list. The tab shows a chip such as "dennis-agent changed spec.ports[name=p2].cable · 3 s ago". The chip has Undo, which writes the inverse of applied with expect.

Undo

  • One history for each (change, file) in the browser session. The page owns it, not CodeMirror. Form and YAML edits share it, and it survives mode and tab switches. Typing in one field within 500 ms is one entry.
  • Writes by others (agent, sync, rebase, other tab) are barriers. The editor applies them outside the history. Ctrl+Z at a barrier asks: "The next undo reverts dennis-agent's edit of spec.ports[name=p2].cable. Undo anyway?" A confirmed undo is a normal write with expect.
  • Git is the durable undo. POST /changes/{id}/restore {paths, to: head | base | <sha>, baseShas} gives "Discard changes in file" and "Restore from main", also as an MCP tool and pk restore. The "worktree is dirty" errors of rebase and ready link to it.

Autosave and drafts

  • Only text that parses reaches the worktree on its own. Autosave, tab switch, mode switch and leaving the page skip a broken buffer. Ctrl+S on broken YAML asks first, because render, labs and agents will see the error.
  • A broken buffer goes to a private draft in the bench data directory, outside the worktree: PUT /changes/{id}/drafts?path=. Render, labs and agents never read drafts. On reopen the editor offers "Restore unsaved draft (2 min ago)".
  • Valid buffers flush on the 750 ms debounce, and also on blur, tab switch, mode switch, commit, lab run and when the page goes hidden.
  • Status line: editing → saving → saved 41b7a2d → rendered (or render failed). A broken buffer shows draft, not in worktree.

Commit

  • The commit names the blobs it reviewed: {message, files: [{path, sha}]}. The bench stages exactly those under the lock. A file that changed after the review gives 409 with who changed it.
  • Before commit mode, a lab run, mark ready and push, the editor waits for pending saves. The staged diff shows the shas it will send.
  • When an MCP agent writes in a change, the bench records the agent in the change metadata. That feeds the Pk-Agent trailer at merge, whoever commits. The commit panel marks files whose last writer was an agent: "written by dennis-agent, not yet reviewed by you".
  • In review or approved state, the commit panel says "This commit resets 2 approvals" and needs a second click.

6Secrets

The design says the editor "decrypts locally with the admin key, shows secret fields masked, and re-encrypts on save". The demo never decrypts, and restores masked values by position. The diagram shows why position fails.

Rule S1 · what git holdsA secret field holds SOPS ciphertext or an OpenBao reference {bao: mount/path#key}. Plaintext is an error: the write API answers 422, and pk check fails. Lab overlays get no exception; twins get generated fake values encrypted with the twin key. The secret field set is the union of schema marks, .sops.yaml encrypted_regex matches, ENC values in the file and chart value overlays.
Rule S2 · masks carry identityA mask is ••••••••‹b7e2›: a short hash of the stored ciphertext or reference. The bench restores by token among the file's stored secrets. It keeps no state, so restarts and second tabs work. An unknown or duplicated token, or a token in a field that is not secret, gives 422 "secret moved or copied". In YAML mode the mask is one atomic token that cannot be edited in part.
Rule S3 · SOPS writes keep the MAC validThe repo sets mac_only_encrypted: true (decision D3), so the MAC covers only the encrypted values.
  • With the key, every write to a file with a top-level sops: block goes through the codec: decrypt → apply ops or text to the plain tree → re-encrypt only the leaves that changed, keeping all other ciphertext byte for byte → recompute MAC and lastmodified → write. Before commit the bench decrypts each changed SOPS file once as a check.
  • Without the key, the bench may change plain leaves and plain subtrees that hold no encrypted value. It leaves the sops: block as it is. An op that adds, removes, moves or reorders an encrypted value, or renames one of its parent keys, gets 422 "needs the SOPS key", because the MAC and the path-bound ciphertext would break. Secret rows show "encrypted for age1q…7k, age1x…9p".
  • Checks. pk check fails when a creation rule or a SOPS file does not set mac_only_encrypted: true, and when an encrypted value sits under a path its creation rule does not encrypt. CI has no key, so it cannot verify the MAC itself.
Rule S4 · who sets a valuesecret.set comes only from a person in the browser or the CLI. The value goes from a password input to the bench and never appears in a read, an event, the history or the LLM log. Agents and accepted suggestions may use secret.generate: the bench makes the value and no model sees it. For OpenBao fields the form edits only the reference; writing the value into OpenBao is a manual step after merge.
Rule S5 · review sees rotationsBecause unchanged ciphertext keeps its bytes (S3), a changed ENC leaf means a changed secret. The bench and CI see this from git alone and add a semantic line "secret spec.values.hubble.ui.auth.token changed (sops)". Policy can rate it: risk: secretChanged: high.
Rule S6 · one masking function for every readUI, MCP, chat, advisor, history and rendered objects (including Secret data) use the same mask. A redactor pattern hit in a file without a secret mark shows as suspected, with the warning "looks like a plaintext secret: encrypt it or allow-list it". The allow-list (.pk/secrets.yaml), .sops.yaml and secret overlays need owner approval in policy. A field that was encrypted on main and is plaintext on the branch is a pk check error.

Validation of SOPS files: with a key, the bench validates the plain tree. Without a key, it checks each ENC leaf against its type: tag, skips content rules and adds the info "encrypted, not validated".

7Checks and problems

Today the browser re-implements some schema rules in TypeScript, the bench has others, and CI checks only path rights, lab gate and approvals. The refined design has one check code base, in four stages.

Problem {
  path, doc, field, line,            # field address (section 1); line only for display
  severity: error | warning | info,
  code, source: yaml | schema | rule | kind | render | policy | secret | overlap,
  message,                           # plain text; the UI never parses it
  related?: { kind, name, path },    # "in use by cn-003" as data, not as text
  origin: change | inherited,        # inherited = already on the base
  cluster?,                          # render problems
  computedFor: <content sha>,        # UI greys out problems for an older buffer
  checkedBy: <platform-kit version> }
Rule V1 · what blocksSave, commit and push are never blocked, so a draft may be broken. error blocks merge in CI. warning shows on the review page and does not block (decision D9). info shows only in the editor. Only new problems block: CI compares base and head by {path, doc, field, code}. A problem that already exists on main shows as inherited.
Rule V2 · mark readyThe bench gives advice only, as section 7 of the design says. A person who marks a change ready with new errors confirms "CI will block: 3 errors". The bench refuses ready for agents, so reviewers never get a broken change from an agent.
Rule V3 · resolution scopePickers, ref checks and kind hooks resolve against the change's own tree, which includes its stack parent. A target that exists only in another open change shows as "pending in c-3w9dqp" (warning).
Rule V4 · source-level overlapMany kinds render no objects (work items, racks, articles). When two open changes set the same {path, doc, field}, both get an overlap warning with a link, next to the existing rendered-object overlap.

8The form

8.1 Coverage: the form is never lossy

  • Every key of the document is reachable from the form. Each object section ends with an Other keys block for keys the schema does not know. In an own kind (additionalProperties: false) the block is an error with Remove. In a third-party or open schema it is editable.
  • A free subtree (type: object without properties, preserve-unknown-fields, widget: yaml) is an embedded YAML block, validated against its sub-schema.
  • Each object section ends with + Add field: the absent optional properties, with description and default.
  • A value whose type does not match the schema (for example unit: "U12") shows raw and read-only with the type error and Replace. The form never shows it as empty and never overwrites it silently.
  • apiVersion and kind are chips in the header. sops is a chip "encrypted (SOPS)". status is not shown.

8.3 Absent, null, empty and default

  1. Clearing an optional field removes the key (unset). Clearing a required field keeps the old value in the file, shows the "required" error and writes nothing until the field has a value.
  2. Every optional select, ref and number has "not set" or a clear button.
  3. An absent field with a schema default shows the default as muted text ("default: 5m"). Without a default it shows "not set".
  4. The form never writes a value the user did not type, and never removes a value only because it equals the default.
  5. Own-kind schemas do not allow null. In third-party kinds an explicit null shows as a read-only chip with Remove key and Open in YAML.

8.4 Lists

  • Where x-pk-list.key exists, problems, change markers, suggestions and secrets use the item key.
  • Items collapse to the summary line with a dot for error or change. A filter box appears above 30 items.
  • Item actions: move up and down (only when ordered), duplicate, delete with an undo toast.
  • A new item comes from schema defaults plus a kind hook NewItem(field, siblings). This replaces the Node port logic in the generic form.
  • A list inside a list item opens as a drill-in with a breadcrumb (ports › p2 › vlans), not inline.

8.5 Change markers

The bench returns the base content with the file: the merge-base with the target, or the parent change in a stack. The form marks each field as added, changed or removed against it: a bar on the row, "was: 5m" under it, Revert field, ghost rows with Restore for removed fields, counts on section headers and list summaries, and a "Show only changed" switch.

9Suggestions, agents and the CLI

A suggestion is one object, made of edit operations. Chat, advisors and LLM form fill all produce it. Nothing from a model writes a file directly; only an MCP agent writes, with its own identity.

Suggestion {
  id, changeId, title,
  origin: { kind: chat | advisor | agent, logId?, recipe?, agentId? },
  basedOnExternalText: bool,         # the turn read MR comments, org data or lab logs
  files: [ { path, doc, ops: [ … canonical field, expect … ] } ],

POST /suggestions/{id}/accept { "ops": [0, 2] }   # one edit-operation write; the commit later gets Pk-Assisted: <logId>
  • Each op is checked against its own field only. An edit elsewhere in the file never makes a suggestion stale. If one op's expect fails, only that op is stale.
  • A model may propose intent and asserted fields only: never derived, generated, secret (except secret.generate) or org-sourced fields, and never on a path the person cannot write. The tool layer reads this from the effective schema.
  • Whole-text suggestions stay only for files without a kind and for Markdown bodies.
  • An agent in suggest mode produces suggestions. An agent in navigate mode writes directly; the form shows the chip with Undo and replays pending edits (decision D10).

10Files and entities

Rule L1 · one entity per fileAn own kind that people address by name stores one entity per file (work/milestones/m-4tq7nz.yaml, as today for nodes). A collection kind (CablePlan, emulation rules, policy) is one entity, and its rows are keyed list items.
  • Entity endpoints. PATCH /changes/{id}/entities/{group}/{kind}/{name} takes ops with fields relative to the entity's document. POST /changes/{id}/entities/{group}/{kind} {name, from?} creates one. The bench resolves the file; CLI, MCP and later entity pages stop resolving on the client.
  • Identity. Each kind declares its identity field and an id scheme that is safe without coordination: random base32 with a kind prefix (like change ids), or a human name that pk check tests for collisions at push.
  • New. When a kind has no skeleton hook, the bench builds the skeleton from the schema: required fields with their defaults, others empty, which show as "fill in" problems.
  • Clone (from: Node/cn-035) clears asserted, generated, secret and x-pk-unique fields and lists each one as a "fill in" problem.
  • Rename. The bench builds one batch from the reverse x-pk-ref index of the change tree: the file move, the identity field and every referencing field. The UI shows the preview before it applies. Git finds the rename by similarity, so no separate commit is needed.
  • Delete lists the backlinks ("3 files reference cn-035") and offers to remove the references in the same batch.
  • Bulk edit. The client selects (entity list filter or --where); the batch endpoint runs with dryRun, shows a grouped semantic diff, and then applies all files or none, with one render and one event. The CLI needs --yes above 20 files.
  • Templates stored in the repo wait until clone proves not enough.

11Versions

  1. An edit keeps the file's stored version and validates with that version's schema. Save never converts. The demo text "saving writes the newest version" goes away.
  2. Upgrade to v1beta1 is an explicit action that writes only the conversion. The commit panel proposes it as its own commit, so it does not mix with the intent edit or collide with the migrate bot.
  3. A version stays editable until the migrate bot has moved all files. Then the kind drops it.
  4. Optional additive fields need no new version. Renames, moves, type changes and new required fields do. A CI test runs every converter over fixtures and validates input and output against the old and the new schema.
  5. New files use the newest version. Time travel shows the stored version, with "Show converted" as a read-only toggle.

12Work kinds in the editor

The work kinds design defines the kinds. The generic editor needs no special code for them; the rules above cover them.

  • Four kinds in work.pk.io: Goal, Milestone, Task, Ask. One file per object in work/{goals,milestones,tasks,asks}/. Ids are a kind prefix plus 6 random base32 characters (t-8kq2vm), so parallel branches never collide.
  • Stored fields are intent. The state, expected date and external ref of an Ask are asserted; their source can be an org system. Status, progress, health, blocked, the change list and the delivery level are derived and never stored: the form shows them read-only with their source.
  • Nesting by reference: the child stores parent; the dependent stores needs: []. The parent's children and an item's changes are derived backlinks (x-pk-ref.inverse). A kind hook reports a cycle in needs as an error.
  • The change holds the link: .pk/changes/<id>.yaml gets work: {closes: [], refs: []}, and the merge writes Pk-Closes and Pk-Work-Item trailers. Work files hold no change ids, so two changes on one item never conflict.
  • Evolution is a field change on the same kind (parent, needs, every, dropped). Kind and id never change. A cross-kind move (Task → Milestone) is Convert…: a batch that creates the new object, sets dropped and replacedBy on the old one and re-parents the children, shown as a preview first.

Decisions

D3 takes the other option: platform-kit requires mac_only_encrypted in the state repo. All other decisions take the recommendation. The rules above follow these decisions.

D1 · Can a person edit a field that an org system owns?

Decided: no. The form locks it and offers "Pull from asset-db" and a link to the owner system. The write API answers 422. This follows "no field has two owners" in design §12.
Not chosen: allow the edit with a warning. The next sync change then reverts it, as today, but now visibly.

D2 · Who may set a secret value?

Decided: people only (secret.set in the browser or a TTY). Agents and suggestions may only use secret.generate, where the bench makes the value and no model sees it.
Not chosen: agents may also set values. The value would then come from a model, against the data boundary in design §10.

D3 · Does every edit of a SOPS file need the admin key?

Decided: no. platform-kit requires mac_only_encrypted: true in the state repo. Every creation rule in .sops.yaml and every SOPS file sets it. This needs SOPS 3.9 or later on the laptops and in Flux. The MAC then covers only the encrypted values, so a plain field such as metadata.namespace can change without the key. Rule S3 says what the bench may do without a key. pk check fails when a rule or a file does not set the flag.
Not chosen: strict, where every edit of a SOPS file needs the key.

D4 · Where does the form turn edits into YAML bytes?

Decided: only on the bench. The form sends ops and adopts the answer. The bench runs on the same laptop, so the round trip is tens of milliseconds, and one splicer means one diff for one edit.
Not chosen: keep the TypeScript splicer for the form, with a shared conformance test suite against the Go splicer.

D5 · May git store a derived value, for example as an override?

Decided: no. A stored derived value is a pk check error. When people need to override a computed value, the kind gets a separate intent field (for example spec.bmc.fixtureOverride).

D6 · Is the path of an own kind binding?

Decided: no, a default. New files go there. A Node elsewhere gets a warning.

D7 · Which base do the change markers in the form use?

Decided: the merge-base with the target, or the parent change in a stack. It shows what this change changes. Changes merged to main since then belong to "behind by N" and the overlap warning.

D8 · Does the bench refuse a commit on a path the person cannot write?

Decided: yes, at commit. The demo already does this, with the same check as CI against the target branch policy. Editing stays possible, with a banner. Design §7 says "UI / bench rights (advice only)" and needs one sentence more.
Not chosen: warn only, and let CI refuse.

D9 · Do warnings block a merge?

Decided: never. Only new errors block. Warnings show on the review page.
Not chosen: a warning needs an acknowledgement in a review comment.

D10 · What happens when an agent writes a file that a person has open?

Decided: follow the agent's steering setting. A navigate-mode agent writes directly; the form shows the chip with Undo and replays the person's pending edits by field. A suggest-mode agent makes suggestions.
Not chosen: agent writes to an open file always become suggestions. This makes the API answer depend on what is on a screen.

Changes to the demo code

Ranked by risk. The first four can corrupt a secret, break Flux, or lose a person's edit.

  1. Secret masks with tokens; restore by token, fail closed (secrets.go).
  2. SOPS codec for writes with the key; plain-field-only writes without it; keep unchanged ciphertext (handlers_files.go). Seed .sops.yaml with mac_only_encrypted: true.
  3. baseSha or expect required on every write; re-apply by field; 409 with theirs; no "Reload" that drops the buffer (EditorPage.svelte, chat/store.go).
  4. External writes outside the undo history (YamlEditor.svelte: addToHistory: false); one page-owned undo history.
  5. Write rules in the bench write path, not in formModel.ts.
  6. Field address grammar in Go; drop the implicit spec. fallback; Problem with doc and related.
  7. Multi-document files: parseAllDocuments in the client, per-document kinds in FileContent, document strip.
  8. Edit operations endpoint; remove the TypeScript splicer from the form.
  9. $defs/$ref schema generation with a visited set and a registration test.
  10. Commit with {path, sha}; await pending saves before commit, lab run, ready and push.
  11. Form: Other keys, Add field, clear = unset, Node port logic out of FormRow.svelte, kind widgets registry.
  12. Remove the "saving writes the newest version" callout; keep the stored version on save.
  13. Work items: drop the changes: field; random ids with kind prefix (see work kinds).
