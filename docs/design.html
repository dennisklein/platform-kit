1. Purpose

platform-kit is the tool to change the desired state of a multi-cluster platform, from bare metal through Kubernetes up to apps. The desired state lives in one git state repo. Flux applies it to the clusters. A git change (worktree, branch, merge request) is the only way to change desired state.

The state repo is on GitLab first. A custom forge with better authorization can replace GitLab later. A local OpenAI-compatible LLM (completion and embedding endpoints) is available on site.

The design puts the mechanics first: change tracking, policy, access, labs and LLM tools. Content entities (racks, nodes, platform components, apps) plug in later on top of these mechanics.

3. Topology

One code base runs in two modes. Mode differences live behind interfaces. No state lives only in the process.

                      ┌──────────── site network / VPN ─────────────┐
 admin laptop         │                                             │
 ┌──────────────────┐ │  push / pull   ┌─────────┐   read, comment, │
 │ bench (local)    │─┼───────────────>│ GitLab  │<── approve ──────┼── shared service ── viewer
 │  UI + worktrees  │ │                │ (forge) │                  │   (SSO)              auditor
 │  MCP endpoint ◄──┼─┼─ agent harness └────┬────┘                  │                      app team
 │  (agent identity)│ │                     │ Flux                  │
 └───────┬──────────┘ │                ┌────▼─────┐                 │
         │ lab driver │                │ clusters │── obs ── Skyhook/Radar
         ▼            │                └──────────┘                 │
   QEMU VMs + BMC     │   LLM: completion + embedder (no secrets)   │
   emulators          └─────────────────────────────────────────────┘
  • Bench (local mode). Runs on each admin laptop. It holds the worktrees, the editor, the lab drivers, the LLM client and the MCP endpoint. All writes start here.
  • Shared service. Runs on a server with SSO. It reads main, branches and MRs. It can comment and approve through the forge as the signed-in user. It holds no worktrees and does not write to git.
  • Network. The bench works on site, over VPN and in air-gapped labs. The LLM and the forge are optional at runtime. Each feature that needs them degrades gracefully.

4. Change model

Change unit

One change is one worktree, one branch and one MR. A large piece of work is split into several changes.

Naming

The branch name is change/<id>-<slug>, for example change/c-k7m2qz-rack-b12. The id is 6 random base32 characters (lowercase, for example c-k7m2qz). The bench makes it offline and checks it against the remote branches at the first push; on a collision it makes a new one. The id is the stable key for the worktree directory, the MR, the lab name and DNS-safe resources. The author is metadata, not part of the name, because a second admin, an agent or the sync bot can also work on a change.

Sharing

Worktrees live on admin laptops. Two admins share a change by push and pull of its branch. The UI shows ahead and behind against the remote branch. There is no lock service.

Stacks

A change can target the branch of one other open change (linear stack). The UI rebases a stack in order. When the parent merges, the child retargets to main.

Change metadata

Git cannot give some data: title, intent, linked lab runs and the stack parent. This data lives in .pk/changes/<id>.yaml in the branch. It is forge-neutral, works offline and travels with push.

# .pk/changes/c-k7m2qz.yaml
id: c-k7m2qz
title: Add rack B12 workers to raven
intent: Add 8 worker nodes in rack B12 for batch jobs.
parent: c-3w9dqp
labRuns:
  - c-k7m2qz/run-3 pass

Open changes

A change stays open until a human closes it. The change rail must stay usable with many open changes: filter, sort and group. See the change rail mock.

5. Change lifecycle

The UI derives each state from git, lab runs, the forge and Flux. It stores no state of its own.

 draft ──> lab ──> review ──> approved ──> merged ──> deployed ──> verified
   ▲        │        │
   └─ fail ─┘        └─ behind target: badge + one-click rebase (change or full stack)
StateDerived from
draftWorktree or branch exists. No MR, or the MR is a draft.
labA lab run for the branch head is running or failed.
reviewMR is open and ready. The lab gate is met if policy needs it.
approvedMR approvals meet policy.
mergedA merge commit with the Pk-Change trailer is on main.
deployedFlux reports the merge commit (or a later one) as applied.
verifiedHealth checks after deploy pass. Empty until observability data is available.
  • Lab gate. Policy sets per path if a green lab run on the branch head is needed before review. For example, Talos and network paths need one; app paths do not.
  • Behind target. The UI shows "behind by N" and offers a one-click rebase. It never rewrites a branch in the background, so a second admin is never surprised.

6. Merge and history

Each MR merges as a merge commit with semi-linear history. The branch must be rebased on its target before merge. Thus main is a straight line of merge commits, one for each change, and each lab run tests the real result.

At merge, the change metadata becomes git trailers of the merge commit. The metadata file is deleted before the merge, so main has no .pk/changes/ files. An auditor lists all changes with git log --merges --format='%(trailers)'.

Merge change c-k7m2qz: add rack B12 to raven (!123)

Pk-Change: c-k7m2qz
Pk-Intent: add 8 worker nodes in rack B12 for batch jobs
Pk-Stack-Parent: c-3w9dqp
Pk-Lab-Run: c-k7m2qz/run-3 pass
Pk-Author: dennis
Pk-Agent: dennis/agent
Approved-by: ...
  • The trailer format is the contract. The forge mechanism that writes it can change.
  • GitLab merge commit templates cannot read files. Thus platform-kit writes the trailers into the MR description, and the template inserts %{description} and the approvers. A custom forge can build the message from the file directly.
  • The commit that deletes the metadata file is part of the move to "review". A commit after approval can reset the approvals.

7. Policy and access

Policy as data

.pk/policy.yaml in the state repo is the root of all rights. It lists people, roles, agents and path rules. The policy schema is defined as Go types. A JSON Schema is generated from them, and the CI policy check and the editor both validate with it. Onboarding is an MR. Only the owner role can approve a change to this file. Keep at least two people in the owner role.

# .pk/policy.yaml
roles:
  owner:          [dennis, anna]
  platform-admin: [dennis, anna, jonas]
  app-team/vault: [lena]
  viewer:         ["*"]
  auditor:        [audit-1]
agents:
  dennis/agent:   { of: dennis, rights: [branch, draft-mr, lab, ready] }
  sync-bot:       { rights: [branch, draft-mr, ready] }
paths:
  - match: control/talos/**
    write: [platform-admin]
    approvals: 2
    lab: required
  - match: control/inventory/**
    write: [platform-admin]
    approvals: 1
    lab: required
  - match: control/apps/vault/**
    write: [platform-admin, app-team/vault]
    approvals: 1
  - match: .pk/policy.yaml
    write: [platform-admin]
    approve: [owner]

Enforcement

                        .pk/policy.yaml
                                │
            ┌───────────────────┼─────────────────────┬──────────────────┐
            ▼                   ▼                     ▼                  ▼
      UI / bench rights   CI policy check      generated GitLab     generated k8s
      (advice only)       (required job)       approval rules,      RoleBindings
                                               CODEOWNERS           (OIDC user name)
  • A required CI job checks each MR against the policy: path rights, lab gate, approvals. The forge blocks the merge if it fails.
  • platform-kit generates GitLab approval rules and CODEOWNERS from the policy and syncs them. Nobody edits generated rules by hand.
  • The UI only gives advice. Main is protected, so nobody can bypass the policy by direct push.

Identity

SSO (OIDC) only proves who a person is. The policy file decides what each person can do. The identity provider needs no groups.

Non-human identities

  • The agent of an admin uses its own identity, not the admin identity. It pushes change branches, opens draft MRs, runs labs and can mark a change ready for review. It never approves, merges or pushes to main.
  • The sync bot has the same rights, without labs.
  • Commits and trailers show the agent and the admin it acts for.

Cluster access

  • kube-apiserver uses OIDC. kubelogin gets short tokens from SSO. platform-kit writes the kubeconfig. Admins keep no long-lived static certificates in ~/.kube/config.
  • platform-kit generates the k8s RoleBindings from the policy file by OIDC user name.
  • Break-glass. A cluster admin certificate is sealed in OpenBao. Any platform admin can get it when SSO or OIDC fails. Each use sends an alert and writes an audit entry. The certificate is rotated after each use.
  • Last resort. When SSO and OpenBao are both down, an admin uses the offline talosconfig of the cluster to get an admin kubeconfig from the nodes (talosctl kubeconfig). Each cluster has one talosconfig, kept offline. Its use is logged after recovery, and the talosconfig is rotated.
  • After each use. All owners and platform admins get an alert. An incident record in git is required, with no deadline. The UI shows each break-glass use without an incident record as an open item until the record exists.

8. Forge interface

The core uses a thin forge interface: MRs, approvals, comments, pipelines and events. GitLab is the first adapter. The custom forge is a second adapter, not a rewrite. No GitLab type leaks into the core.

9. Editor, rendering and secrets

Schema-driven editor

The first editor is generic. It edits any repo file through a schema-driven form, on all layers. Schemas for repo files are a core contract. Dedicated entity pages (racks, nodes, platform components, apps) come later on top of the same schemas. Schemas also mark secret fields and the owner system of each field (see org database sync).

Kind registry

A kind is a type of repo content (for example a rack, a node, a cable, a Flux Kustomization). Each kind is a Go package compiled into platform-kit. It registers:

  • Schema. Own kinds define Go types. The types generate a JSON Schema with platform-kit extensions (secret, field owner, truth class, references to other objects, UI hints). When the kind is a k8s object, the same types also generate the CRD schema. Third-party kinds (Flux, Cilium) reuse their CRD schema plus a small overlay for UI hints.
  • Truth class. One of intent (people write it), generated (render output), asserted (a claim about the physical world, for example a serial number), derived (computed from other data) or imperative-only (no reconciler). Editor, sync, LLM and lab rules use it.
  • Apply path. Flux, manual (for example talosctl or an OpenBao configure script) or sync. The UI shows manual apply paths as open steps after merge.
  • Hooks. Views, semantic diff, cross-file validation (for example "this cable connects two known ports").
 repo file ──> kind registry ──match──> kind: schema · truth class · apply path · hooks
                    │
                    └── no kind ──> YAML editor (+ CRD schema validation if apiVersion/kind matches)

Schema evolution. Kinds have versions (v1alpha1, v1beta1, v1). Each new version ships a converter from the old one, so the UI reads all old versions (time travel, audit). A migrate bot opens a normal change that moves the repo files to the new version.

Files without a kind. The UI edits them in a plain YAML editor. If a known CRD schema matches their apiVersion and kind, the editor adds validation and completion. Thus the UI is useful for all files from day 1, and each new kind only improves it.

Rendered diff

Rendered manifests are not committed. CI and the bench render main and the branch, and show the object diff on the MR. Flux still renders in the cluster. Reviewers and the LLM see final objects, and rebases have no conflicts in generated files. The renderer reads the Flux version from the Flux manifests in the repo and uses the matching kustomize and helm libraries. Thus a Flux upgrade MR also shows the render with the new versions.

Secrets

  • Talos and bootstrap secrets stay in git, encrypted with SOPS. They must exist before OpenBao runs.
  • App secrets move to OpenBao references over time.
  • The editor has one "secret field" concept for both. It decrypts locally with the admin key, shows secret fields masked, and re-encrypts on save.

10. LLM integration

One tool layer serves three surfaces. Each surface starts small.

              ┌─────────── tool layer (read repo, read changes, draft edits, run lab, ...) ──┐
 agent  ──MCP─┤                                                                               │
 chat   ──────┤──> redaction (no secrets) ──> local LLM (completion) + embedder (retrieval)  │
 advisor──────┤                                                                               │
              └───────────────────────────────────────────────────────────────────────────────┘
  • MCP endpoint. The bench exposes MCP on 127.0.0.1 with a bearer token for each agent. A token lives about 8 hours; the admin approves the agent again each workday.
  • Freeform chat. Chat in the UI that can see the project, through the same tools.
  • Advisory buttons. Opinionated, retrieval-based help on fixed questions (for example "risks of this change"), like Skyhook/Radar. No freeform input.
  • Data boundary. The LLM sees all data except secrets and credentials. A hard redaction filter runs before each call. IPs and serial numbers stay visible.
  • Retrieval. The index uses the local Qwen embedder and stays on site.
  • Logs. All prompts and answers are kept with no time limit. A UI page lets platform admins search, export and delete entries. The log is a sensitive store: on site, platform admins only, with backup. Each delete writes an audit entry.

11. Labs and live state

Labs

Labs come first. A lab runs desired state on emulated hardware. It has two purposes:

  • Digital twin. A long-lived lab that follows main. Admins and app teams use it to explore, learn and develop apps and platform parts.
  • Change lab. A short-lived lab for one change. It starts at a base ref, applies the change, runs a scenario and writes a report. The lab gate of a path (section 5) needs a green change lab.
 control/inventory + cabling.yaml + talconfig + .pk/emulation.yaml
                         │ generate
                         ▼
   Topology  (per machine: Redfish sim + qemu | talos-docker | none, NICs on VLAN networks)
        ▲                                        ▲
 Lab purpose: twin                        Lab purpose: change
 follows main, overlays/twin,             base ref + change ref, scenario
 persistent, nightly snapshot ──────────> (checks, BMC power, sim faults), report

Hardware emulation

Each real machine maps to three emulated parts:

PartEmulator
BMCGo Redfish sim with captured vendor fixtures (for example supermicro-x12, huawei-2288h-v5), with fault injection.
Machineqemu (UEFI, disks, Talos install, reboot), talos-docker (fast), or none (BMC only).
Networkcontainerlab builds the VLAN networks, links from cabling.yaml and the routers (FRR). QEMU VMs attach by tap. The uplink is NAT only, never into the real site.

.pk/emulation.yaml maps inventory facts (model, role) to emulators and VM sizes. platform-kit generates the Topology from the desired state; nobody writes it by hand. Parts that cannot be emulated (for example InfiniBand) are marked emulate: false.

Lab rules

  • Definitions. Labs are derived from desired state (twin and change labs), or written by hand for experiments (.pk/labs/<name>.yaml, inline topology).
  • Lab-only differences. A twin uses a kustomize overlay next to the live one (control/overlays/twin) and Flux post-build variables.
  • Fidelity. A twin can be scaled (a subset of machines, cheap backends). A change lab can be a full replica where the change needs it (HA, network).
  • Provisioning. A switch on each lab: metal boots through the emulated BMCs, vMedia and the Talos install; direct injects the Talos config. Twins default to direct; change labs for inventory and Talos paths use metal.
  • Fresh or snapshot. Policy chooses per path. Bare-metal paths get fresh machines; platform and app paths start from the nightly twin snapshot.
  • Lab hosts. One lab driver interface, two targets: the laptop for small labs (also air-gapped), and a lab host for full replicas and CI gates. Bridges and taps need root or CAP_NET_ADMIN on the lab host.
  • Lab object. A lab is defined as a file in git (.pk/labs/<name>.yaml) or generated. At run time the bench applies it as a Lab custom resource to a small lab control cluster (kind). A lab controller reconciles it and reports status conditions, as the metal operator does. Laptop and lab host run the same controller.
  • Twin secrets. A twin has its own SOPS key. platform-kit generates fake values for each secret field that the schema marks. No live secret reaches a lab.
  • Org services. Labs run stub services: fake DNS, a local ACME CA and a fake sync adapter. The twin overlay points to them. A lab never writes to real org services, and twins work air-gapped.
  • Scenario steps. Built-in step types: check, gitops, bmc, fault and wait. An exec step runs a container image for custom checks, so teams add checks without a lab controller release.
  • Results. Raw results (conditions, events, console logs, Flux status) stay on the host where the lab ran. It is recommended to add a report to the change, as a normal document in the state repo (for example a knowledge base article), where it fits. The Pk-Lab-Run trailer names the run and, if present, the report path.
  • Code. A separate lab Go module holds the sim, the machine backends and the network setup. The metal operator tests and platform-kit both import it.

See lab configuration examples.

Live state

The target is a full observability overlay on desired state: Flux status, object diff, metrics, alerts and logs per entity. It comes after labs. At the start, platform-kit links to Skyhook/Radar instead of its own views.

12. Org database sync

  • The first org systems are not known yet. A generic sync adapter interface keeps vendor schemas out of the core.
  • Each field has one owner system. Sync goes both ways. No field has two owners. Schemas mark the owner.
  • The sync bot opens a normal change on a schedule. An admin can also pull org data into an open change.
  • On drift, the field owner wins, and the sync MR shows the diff for review. Drift never changes main without an MR.
