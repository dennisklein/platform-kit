Work kinds, lifecycles and progress reports

This document defines a small set of work kinds for platform-kit. It defines their lifecycles, how they nest, how they change over time, and how they relate to a change. It then shows how an executive progress report comes from a semantic diff of the work kinds between two dates.

Base: design.html, the demo branch (PR #3: internal/kinds/work, the work board), and the design talk of 30 Oct 2026. Sample data uses the demo content (defiant, rack GC5A-6Z, cn-035).

0Short answer

  • Four kinds: Goal (why), Milestone (when), Task (our work, done by changes), Ask (work that others do for us, for example your "org task").
  • A kind is defined by where its status comes from. Task status comes from changes. Milestone and Goal status comes from their children. Ask status is asserted by a person or by the sync bot. No status is typed by hand.
  • Nesting is fixed and shallow: Goal › Milestone › Task › Sub-task, plus Asks as leaves. Maximum 4 levels of our own work. A milestone never contains a milestone.
  • Evolution is by addition. A task gets sub-tasks, Asks or needs edges. Its kind and its id never change. A real kind change (task becomes milestone) is a supersede: a new object, and the old one points to it.
  • A change is required for each edit, as you said. Plan-only changes get a fast path in policy. The link between a change and a task lives in the change, not in the task file. Thus parallel changes do not conflict.
  • The 1:1 case (one task, one change) shows the full change state as the task state. The demo already allows N changes per item; this design keeps that and adds a "closes" flag.
  • A progress report is a semantic diff of the work view between two baselines. Code computes the numbers. The LLM drafts words with citations. A person owns the text. The report is a file in git, added by a change.

2Principles

  1. Git is the only write path. Each work object is a file in the state repo. A change adds or edits it. This gives review, audit and history for free.
  2. Store intent, derive status. People write scope, dates, owners and links. The bench computes status, progress and health. Nobody types "done".
  3. A kind is its status source. A new kind is only necessary when status comes from a new source. This keeps the set small.
  4. Evolve by addition. Ids and kinds never change. Growth adds children, Asks or needs edges. Thus a report can follow each object over years.
  5. Links point from the newer or dependent object. A child names its parent, a dependent names its dependency, a change names its task. Then two parallel changes almost never edit the same file.
  6. A report is a diff between two baselines. The same semantic diff hooks that describe a change also describe a month.
  7. Code computes numbers, the LLM writes words, a person owns them. Each health rating names the rule and the inputs, so a reviewer can check it.

Not stored anywhere in a work file: status, progress, health, the blocked flag, the list of changes, and the children. The bench computes them. The editor shows them read-only.

Why not fewer kinds, and why not more

  • One generic "item" kind is simpler to store, but then a field must say what kind of status applies. Executives also need a fixed "goal" and "milestone" layer that does not change shape. Four fixed kinds make the report stable for years.
  • No separate Epic, Story, Bug, Request or Risk kind. An epic is a task with sub-tasks. A bug or app-team request is a task in the inbox. A risk is computed (see health rules). A recurring task is a task with every.
  • No Sprint or Iteration. A small team does not need time boxes. The report period is the only time box.

4Nesting and dependencies

There are two relations. parent means "is part of". Progress rolls up along it, and a parent cannot be done while a child is open. needs means "must wait for". It crosses the tree and it does not roll up.

Rules (cross-file validation, error in CI)
  1. A Milestone has no Milestone as parent. Use needs to order milestones, and a Goal to group them. Nested dates make conflicts that nobody can solve.
  2. A sub-task has no sub-task. When a sub-task must split, split it into siblings. When that is not sufficient, promote the parent task to a milestone (see evolution).
  3. A recurring task is never in a milestone. A milestone must end, and a recurring task never ends.
  4. The needs graph has no cycle, and an object does not need its own ancestor or descendant (the tree already says that).
  5. A done milestone takes no new children. Put new work into a follow-up milestone. This keeps "delivered on" dates true.
  6. Warning, not error: a task without a parent for more than 14 days ("inbox"), and a needs edge to a dropped object.

5Lifecycles

Each lifecycle below is computed. The only states that people set are the Ask states and the dropped and result fields.

Task status: the exact rule

dropped  if the file has dropped: {...}
done     if no own change is open, and
           (no children and a closing change is merged)
           or (children exist and each child is done or dropped)
active   if an own change is open, or an own change is merged but none closes,
         or a child is active or done
planned  in all other cases
blocked  (flag) if not done, and a needed object or a child Ask is not done/delivered

delivery level of a done task = lowest level of its closing changes and children:
  merged  <  deployed@lab  <  deployed@canary  <  deployed@prod  <  verified@prod

A closed MR that did not merge does not count. A revert change of a closing change sets the task back to active and the report says so.

The 1:1 case

Most tasks have one change and no children. Then the task shows the seven change states from design section 5, not the coarse status. The board column comes from the coarse status.

Recurring tasks

A task with every: 1mo (or 1w, 3mo, 1y) never becomes done. Each period is done when a closing change merges in that period. When a period ends without one, the task is overdue. Examples: the monthly executive report, the Talos upgrade each quarter, the monthly DR restore test. To stop a routine, drop it.

Milestone and goal health

Health uses rules in .pk/work.yaml, in the same way that .pk/policy.yaml rates the risk of a change. Each result names the rule and its inputs. The advisor may add a note, but it never sets the health.

# .pk/work.yaml
health:
  late: due passed and not done
  atRisk:
    - rule: ask-late           # a needed Ask expects delivery after due - buffer
      buffer: 7d
    - rule: ask-not-requested  # an Ask is still "open" and due is near
      within: 21d
    - rule: throughput         # open leaf tasks > done per week (last 8 w) x weeks left
      window: 8w
    - rule: stale              # an active task had no change activity
      after: 21d
reports:
  every: 1mo
  depth: milestone            # executives see goals and milestones; tasks only as exceptions
  delivered: deployed@prod    # what "delivered" means in a report

Progress of a milestone is the count of done leaf tasks divided by all leaf tasks that are not dropped. A leaf task is a task without sub-tasks. Asks are not counted, because they are not our work. They show as blockers.

    write: [platform-admin]

  minHumanApprovals: 1    # no 0-approval path when an agent or bot authored the change

The fast path does not weaken the audit. Each plan edit is still an MR with trailers, an author and a CI policy check. The bench does the whole cycle with one click ("Save plan"). When an agent or the sync bot is an author, the fast path does not apply. A human must approve, and the person the agent acts for can be that approver. Reason: an agent never merges, and repo text that the agent read could carry an injected instruction.

Rule: plan edits do not hide in a delivery branch

You often find a new Ask or sub-task while a delivery change is open. If you add that file in the delivery branch, main shows it only after the merge. But the merge waits for the Ask. So the bench puts each work edit into a separate quick plan change by default ("side change"), and main shows the blocker at once. Exception: an inline change can create the one task that it closes.

The two cases you named

A simple task needs an org task

Anna works on c-p4x8ma for t-9rb3ne (BGP peers). She finds that the org routers need open uplink ports. The network team must do that.

  1. On the task, she clicks Add Ask. She types the party and the ticket.
  2. The bench writes work/asks/a-5xk2pq.yaml and adds needs: [a-5xk2pq] to the task, in a side plan change. It merges with one click.
  3. The task shows blocked. Milestone health uses the expected date of the Ask.
  4. Her delivery change stays open. When the Ask is delivered, the flag goes away.
A simple task needs sub-items

t-6mz4ca (Ceph pool for tenants) turns out to need disks, a pool and quotas.

  1. Click Split. Enter three sub-tasks. Optional: order them with needs.
  2. The bench writes three files with parent: t-6mz4ca. The task file itself does not change.
  3. The task status now comes from its children. Milestone progress counts 3 leaves instead of 1.
  4. If a sub-task needs to split again, the bench offers Promote to milestone. That is a supersede.

Supersede, step by step

Kind and file path stay fixed for each id. A kind change is therefore a new object. Example: promote t-6mz4ca to a milestone.

# one plan change, made by the "Promote to milestone" action
+ work/milestones/m-2vx6pn.yaml     title: tenant storage, parent: g-4hd2ka, due: 2027-01-31
~ work/tasks/t-6mz4ca.yaml          dropped: {reason: grew into a milestone, replacedBy: m-2vx6pn}
~ work/tasks/t-h3d9tw.yaml          parent: t-6mz4ca → m-2vx6pn   # each sub-task moves up one level
~ work/tasks/t-w8e2rf.yaml          parent: t-6mz4ca → m-2vx6pn
# open changes that close t-6mz4ca: the bench offers to retarget them to m-2vx6pn's tasks

The report follows replacedBy edges, so the history of t-6mz4ca continues in m-2vx6pn. Nothing is renamed.

9Progress reports from semantic diffs

Yes, a diff of the work kinds is the right basis. There is one problem to solve first. The report needs two kinds of fact, and only one of them is in git.

Intent facts: in git

Scope, parents, dates, owners, Ask states. git show <baseline>:work/ gives them for any date. A diff of two trees gives "added", "dropped", "moved", "re-dated".

Derived facts: not fully in git

Status comes from the forge, Flux and labs. Merges are in git (trailers). But "in review on 1 Oct" or "deployed to prod on 1 Oct" may not be recoverable later. So each report freezes a snapshot of the derived facts.

The baseline chain

Each report is a record file. It holds the baseline (the last merged change at the cut-off time; not a commit hash, see the SHA-256 decision), the frozen snapshot and the computed diff against the previous report. The next report diffs against it. Thus the reports form a chain that nobody can change silently.

# work/reports/r-2026-11.yaml  (kind: Report, record)
apiVersion: work.pk.io/v1alpha1
kind: Report
id: r-2026-11
period: {from: 2026-10-01, to: 2026-11-01}
previous: r-2026-10
baseline: {lastChange: c-v2n8kd}        # state of main at the cut-off
snapshot:                               # generated: Go code writes it, CI recomputes and compares
  m-7tq1xe: {status: active, health: at-risk, done: 4, of: 9, due: 2026-12-14}
  t-2fp6wd: {status: done, level: verified@prod, by: c-31d0aa}
  a-5xk2pq: {state: promised, expected: 2026-12-08}
diff:                                   # generated: semantic lines, each with a source
  - {id: d1, section: delivered, subject: t-2fp6wd, text: Cabling for GC5A-6Z verified on prod, source: c-31d0aa}
  - {id: d7, section: schedule, subject: m-7tq1xe, text: due 30 Nov → 14 Dec (+14 d), source: c-q7c1nb}
  - {id: d9, section: blockers, subject: a-5xk2pq, text: network team promised ports for 8 Dec, source: c-b5t0ye}
narrative: |                            # intent: drafted by the LLM, edited and owned by a person
  Rack GC5A-6Z is cabled and in production [d1]. The milestone moved by two weeks
  because the org router ports arrive on 8 Dec [d7][d9].

Exception rule for depth. Executives see goals and milestones. A task appears only when it is blocked for more than 14 days, when its Ask is late, or when it changed a milestone health. All other tasks show as counts.

Scope honesty. Progress can go down when scope grows. The burn-up chart shows both lines (total scope and done), so a reader sees why. The diff names each scope change and its reason.

12Migration from the demo

  1. Add the kinds Goal, Milestone, Task, Ask and Report in work.pk.io/v1alpha2.
  2. Converter WorkItem v1alpha1 → Task v1alpha2: milestone becomes parent; changes moves out of the file (the bench reads it from history and change metadata); id w-104 stays as an alias in aliases: [w-104] so old trailers still resolve.
  3. Converter MilestoneList → Milestone files, one per entry.
  4. A migrate bot opens one normal change that moves the files (design section 9, schema evolution).
  5. Change metadata gets work: {closes, refs}. The old workItems list reads as closes.
  6. The work board keeps its four columns. Plan, Roadmap and Reports are new tabs.
